Tiny MoE harness v0: deterministic on 2× T4, and MoE beats dense at equal active FFN width

This is my contribution to the team comparison agreed on the 26 Oct call: a config, a config checker and a training harness. The harness trains a Kronecker-embedding MoE decoder with Muon+AdamW and supports DP, TP, PP and ZeRO-1. Two runs with seed 1234 give byte-identical loss at every step. The MoE sweep below ran on Kaggle in the same notebook runtime as the harness.

What the 26 Oct call asked for

  • Four files due Tue 27 Oct: the MoE config, the config check, the harness and plan_v0. Tomorrow's submission is a skeleton: keys and structure matter now, and the values come later from TSAI (Rohan).
  • Each person pushes their own code under their own folder in this repo tonight. The team then cherry-picks the best parts into the skeleton for the main ERA-V5 repo.
  • Known gaps in every config: the data-mixture weights and the distributed parameters (dp, tp, pp). SmolLM3 and nanotron are the reference for stage weighting and parallelism keys.
  • Seed 1234: two runs must give the same loss at every step.

This folder answers both gaps. Data weighting uses SmolLM3-style data_stages (stable → stage2 → anneal at 0 / 0.73 / 0.82 of the steps), and the parallelism block uses nanotron ParallelismArgs names (dp, tp, pp, pp_engine, tp_mode, zero_stage, recompute_layer, expert_parallel_size). Both run on real hardware.

Config

  • configs/config_v0.yaml: every leaf has a # source comment, citing the KE code / arXiv 2605.29459, lessons, an Admin ruling, or SmolLM3. The sizes are open_keys.
  • harness/check_config.py: 0 errors, 15 open. Every small config: 0 errors, 1 open (the KE2 shape from G4).
  • Small configs extends: a parent with deep merge. configs/small/t4_moe.yaml is the G6 file.

Harness

  • torchrun harness/train.py --config C --out DIR [--set k=v]
  • A batch depends only on (seed, step), never on the layout, so DP, TP and PP see identical data.
  • Outputs: losses.tsv (exact repr), metrics.jsonl with the six G8 names, checkpoints. On NaN: NAN_REPORT.json plus the resume command.

MoE iteration: 1,000 steps, DP=2, same notebook runtime

Every MoE arm keeps the active FFN width per token equal to the dense d_ff of 768 (top_k × d_ff + shared × d_ff). The comparison is therefore about routing and capacity, not extra compute per token. Everything else is identical: seed 1234, the same data stream, WSD with lr 3e-4, 4 layers, d_model 256, seq 256, global batch 16.

Read with care: this is one seed and 1,000 steps on about 9M tokens. The gaps are small (≤ 0.033 nats) but consistent from step 500 onward. Every MoE arm beats dense. The shared expert with top-1 and the 8-expert top-2 arm lead. The fine-grained arm with 16 experts and top-4 balances best but is 2.7× slower on T4, because the reference expert loop doesn't fuse. A 6th arm with no load balancing, testing for router collapse, hit a logging bug (now fixed); its re-run is pending.

Throughput by layout

TP is slow on T4 because it all-reduces over PCIe at this tiny width. PP holds about 1/10 of the parameters per rank, since the 131K head sits on the last stage.

Bugs found on real hardware (all fixed)

  • PP crashed on torch 2.11: PipelineStage validates input strides, and x[:, :-1] is non-contiguous. Fixed with .contiguous(). Local torch 2.14 never showed it.
  • DDP over gloo failed to broadcast an int16 length buffer. Fixed by storing it as int64.
  • compare_runs --exact passed two empty loss files, so a crash looked like a pass. It now fails.
  • MoE metrics crashed when seq_aux_loss_coef = 0. Fixed.
  • The lab pr-guard email regex matched a top-level decorator line in the diff. Rewritten as a with block.
